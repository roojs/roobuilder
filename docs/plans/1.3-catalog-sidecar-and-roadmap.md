## ✔️ Phase 3 — JavaScript round-trip: use the braced-code standard

Status: ✔️ — tokenizer line-scans code bodies; **0 FAIL** (2026-08-28)

### ✔️ 3.1 Emit / store

Writer + `CodeParts` — canonical shape:

```
Function renderer = function(v,x,r) {
  return v;
}
```

Not flat:

```
renderer = function(v,x,r) { return v; };
```

### ✔️ 3.2 Read back

Parser `take_assign_code()` / `take_code_parts()` split `header {` + body from the `{}` group.

### ✔️ 3.3 Tokenizer

**Rule:** code body `{` → line-scan to `}` at opener indent. Interior is opaque text.

Opener detection uses `line_prefix` (text on the line before `{`):

```
click function (e) {          ← ends with )
Function renderer = function(v,x,r) {   ← = function…
renderer = function(v) {     ← = function…
Boolean hidden = (function() { ← IIFE; closer `})()` at same indent
  return 1;
})()
data                         ← bare method name; `{` on next line
{
  (function() { … })()
}
```

Wrong Writer emit (content below statement indent — never do this):

```
Boolean hidden = (function() {
    return 1;
})();
```

Right (closer at pad):

```
Boolean hidden = (function() {
  return 1;
})()
```

Wrong (structural scan inside the body — quotes / `[` / nested `{` break):

```
Unterminated string
Unmatched ]
```

Wrong (opaque-at-BOL on every `{` — treats `@[` RAW literals as code bodies):

```
fields = @[
    {
        'name': 'id',
    }
];
```

That `{` is a JSON-ish object inside `@[]`, not a listener body. Only opaque when the line before `{` is a code header (`) {`, `= function…`, `init`, bare method name, etc.).

Structural (unchanged): `Roo.LayoutRegion {`, `layout = Roo.BorderLayout {`, `@[ { … } ]`.

## ✔️ Phase 4 — Generated JavaScript must match after VBP round-trip

Status: ✔️ format series done (**4.1–4.8**, **4.10**, **4.11**). Leftover `GEN_DIFF` is `_strings` / Phase 5 (e.g. Login `value = 0`). 🚫 no further 4.x from those counts.


### What this phase is

Phase 3 is ✔️: every file **parses** (no `FAIL`). That only means BJS → VBP → BJS tree load works.

Phase 4 asks a harder question: does the **generated `.js`** from the tree after that round-trip match the `.js` from the tree before?

```
load BJS
  → generate JS          (= “before”)
  → write VBP
  → parse VBP back into tree
  → generate JS again    (= “after”)
```

If before ≠ after (ignoring whitespace / comment noise), the test prints:

```
GEN_DIFF Pman.Dialog.Login.bjs
```

So: **same UI tree went through VBP and came back producing different JavaScript.** Something in Writer, Parser, or codegen is changing meaning (or dropping / inventing props).

`FAIL` = could not parse. `GEN_DIFF` = parsed fine, but the JS output changed.

**Out of scope here:** `_strings` / `_named_strings` catalog matching — that is the Phase 5 sidecar. Phase 4 is structural / meaning diffs in the generated widget JS.

### How to look at one file

```bash
./tests/test_vbp_roundtrip.sh tests/vbp-roundtrip-js.manifest build/vbp-roundtrip-js 2>&1 | tee /tmp/rt-js.log
grep '^GEN_DIFF ' /tmp/rt-js.log
```

For each name, diff the two generated files (paths are flat under the project dir):

```bash
diff -u \
  build/vbp-roundtrip-js/Pman.Admin/Pman.Dialog.Login.bjs.original.generated.js \
  build/vbp-roundtrip-js/Pman.Admin/Pman.Dialog.Login.bjs.roundtrip.generated.js
```

Also useful: the VBP itself and the two BJS snapshots:

```
…Login.bjs.vbp
…Login.bjs.original.bjs
…Login.bjs.roundtrip.bjs
```

Fix Writer / Parser / `NodeToJs` until that file drops off `GEN_DIFF`. Repeat.

### 🚫 4.3 — `_strings` / named_strings noise (not Phase 4)

🔷 Translation catalog lives in a **separate `.bjs` sidecar** (Phase 5). 🚫 Do not treat `_strings` / `_named_strings` drift in generated JS as the Phase 4 work item.

**Login example — show the trigger, not the symptom.**

Trigger in VBP:

```
String name = "logout_other_windows";
Mixed value = 0;
```

(also nearby: `String valueOff = 0;`)

What happens today:

- Original tree: `value` is a normal PROP → `findTransStrings` sees prop name `value` (in `doubleStringProps`) and stores `"0"` in `_strings` / `logout_other_windows_value`.
- After VBP: same line often comes back as RAW → `findTransStrings` skips RAW → those lines vanish → `GEN_DIFF` on the string table.

That is not a real UI/codegen bug worth chasing in Phase 4:

```
value = 0;    ← number — should never be a translation string
```

Ignore numeric / non-text values in the translation walk (or strip `_strings` / `_named_strings` from the GEN_DIFF compare). Real named-string catalog work stays in Phase 5.

### ✔️ 4.4 — `@` fence leaks into generated JS

**Was ~89 files.** Trigger in VBP (correct):

```
sortInfo = @{ direction : 'ASC', field: 'id' };
```

Wrong JS after round-trip (`take_assign_code` treated `@` as a code header):

```js
sortInfo : @ {
```

Right JS:

```js
sortInfo : { direction : 'ASC', field: 'id' },
```

Fix: `take_assign_code` returns null when RHS starts with `@`; `take_value` stores `{ … }` / `[ … ]` only.

### ✔️ 4.5 — typed `Function … = function() { };` missing semicolon (~60 files)

Trigger was Writer `put_code` with no `;` after object-body assigns:

```
Function valueRenderer = function() {
  return String.format("<span style='color:red;'>{0}</span>", ret);
}                    ← missing ;
Number width = 900;
```

`take_value` reads to `;` and ate `Number` into the function body.

Fix: `put_code(..., semicolon)` — `true` for `name = function… { };`, `false` for list peers / `init`.

### ✔️ 4.6 — IIFE `(function… { … })()` trailer

Only format we use. Helpers on `CodeParts`:

```
is_iife_header("(function() …")  → true
iife_trailer()                   → ")()"
```

Trigger (method or prop):

```
data (function() {
  return ret;
})()
```

Was: `take_code_parts` dropped tokens after `}`, so `)()` vanished.  
Now: capture trailer after `{}`; if IIFE header and trailer empty, default `)()`.

### ✔️ 4.7 — do not `@`-fence empty `[]` / `{}`

Rule from 1.0 was too blunt: “RAW starts with `[`/`{` → emit `@`”.  
Real reason for `@`: nested content would be misread as VBP children.

Needs `@`:

```
fields = @[
  { 'name': 'id', 'type': 'int' }
];
```

Does **not** need `@` — nothing inside:

```
fields = [];
```

Was (Writer always prefixed `@`):

```
fields = @[];
```

Tokenizer then glued `@[]` into one TEXT token → prop_val `"@[]"` → JS `fields : @[]`.

Now Writer skips the fence when the literal is empty (`[]` / `[ ]` / `{}` / `{ }`):

```
fields = [];
```

### ✔️ 4.8 — METHOD value starting with `[` → RAW

Legacy `| data` arrays are not functions. In `CodeParts.normalize_tree` (before VBP write):

```
if METHOD and prop_val starts with `[` → node_type = RAW
```

Was:

```
methods [
  data

  }
]
```

Now:

```

## ⏳ Phase 5 — Catalog `.bjs` sidecar on save

Status: ⏳

### ℹ️ What exists today (investigation)

Legacy `.bjs` on disk is a **full UI tree** (`items[]`) plus translation maps. Catalog keys are **not** stored — [`Pman.Core/Bjs.php`](/home/alan/gitlive/Pman.Core/Bjs.php) walks the tree at runtime for AI.

| Consumer | Reads |
|----------|--------|
| `InterfaceTranslations` / `UpdateBjsTemplates` | `strings` only |
| `Pman.Ai/Catalog` + `UiDescribe` | `Pman_Core_Bjs` → fields / urls / titles / tabs / cols |

**Bugs in the current PHP digest (do not copy into the sidecar):**

- 🚫 Top-level `fieldDetails` is a **map keyed by name** — CmsBlog has `id`×2, `title`×2, `add_link`×3 across **9 Forms**; the map keeps one. Name-only `fields[]` has the same collision problem.
- 🚫 Flat top-level `urls[]` dumps every Form.url + HttpProxy + Grid `tableName` into one list — loses which table belongs to which form / tab / grid.
- ℹ️ Tab scope is closer: `tabs[].fields` is already an **array of `{name,label,type}`**, and `relatedTables` is an array — but still no per-form grouping when one tab has multiple Forms.

🚫 **Not** extracted (still out of scope): combo static options, displayField/valueField, JsonReader schemas, listeners. AI gets column/enum semantics from `table_description.ini` + `fetch_data`.

### 🔷 Sidecar shape — forms / grids as groups (arrays only)

One entry per **Form** and per **GridPanel**. Fields are always an **array of objects** — never a name→detail map, never a parallel name-only list.

- **`forms[]`** — each `Roo.form.Form`:
  - `table` — from Form `url` (`/Roo/{table}`) — may be `""` if missing
  - `fields[]` — `{ name, label, type }` in tree order (`type` = xtype)
  - `lookups[]` — tables from **HttpProxy** under that form (combo stores), not the submit URL
- **`grids[]`** — each `GridPanel`:
  - `table` — from `tableName` (or proxy url if that is what we lock)
  - `cols[]` — `{ dataIndex, header, width }`
- **`tabs[]`** — when the dialog has tab regions: nest **`forms` / `grids` inside the tab** (same shapes). Multi-table tab = multiple forms and/or grids in that tab. No flat sibling `urls`.
- **`title`** — primary dialog/tab title (string). Drop redundant `titles[]` unless we keep it as 💩.
- Header: `format`, `name`, `parent`, `modOrder`, `permname`, `strings`, `named_strings`.

Derived `relatedTables` for Catalog = unique of every `forms[].table` + `forms[].lookups[]` + `grids[].table` (PHP can compute; optional sidecar convenience key 💩).

Canonical copy also in [`1.0-vbp-format.md`](1.0-vbp-format.md) § Generated `.bjs`.

### Rules

- 🔷 `fields` = **array of `{name,label,type}`** only. 🚫 No `fieldDetails` map. 🚫 No parallel name-only `fields` string list.
- 🔷 Multiple Forms → multiple `forms[]` entries (same `table` allowed). Overlapping `name`s stay distinct by form index.
- 🔷 Multiple tables in one tab → multiple `forms` / `grids` **inside that tab**. 🚫 Flat dialog-level `urls[]`.
- 🔷 Form submit table vs combo stores: `table` vs `lookups[]`.
- 🔷 `cols` live on `grids[]`, not a dialog-global bag (unless no tab/grid grouping is possible — then top-level `grids[]`).

VBP source (author text, no checksums / no catalog):

```
