## Remaining Phase 4 work (only this — then Phase 4 is finished)

**4.10 — leading `|` on prop names means “raw JS value”, not a character to print in VBP**

When this is fixed, Phase 4 is done. Do not invent more 4.x items from undifferentiated `GEN_DIFF` counts. Anything left that is only `_strings` / `_named_strings` is **Phase 5**.

In old BJS, a key like `"|url"` means: store a raw JavaScript expression under that config key. The pipe is a **flag on the name**, not part of the VBP spelling. Listeners already drop it on write (`|click` → `click`). Value props still emit a literal `|`, which the tokenizer splits, so the prop vanishes.

### Example A — `|url` (JS expression string)

**File:** `/home/alan/gitlive/Pman.Cms/Pman.Dialog.CmsCategory.bjs`

**In BJS (disk v1 `items`):**

```json
"|url": "baseURL + '/Roo/Category.php'"
```

**In-memory tree before VBP (original.bjs snapshot):**

```json
{
  "node-type": 2,
  "prop-name": "|url",
  "prop-val": "baseURL + '/Roo/Category.php'"
}
```

(`node-type` 2 = PROP)

**Writer outputs today (wrong — pipe in the name):**

```
|url = "baseURL + '/Roo/Category.php'";
```

Tokenizer stops TEXT at `|`, so this is not one name. Parser drops it.

**Round-trip tree:** no `url` / `|url` at all.

**Generated JS before round-trip:**

```js
xtype : 'Form',
'|url' : 'baseURL + \'/Roo/Category.php\'',
method : 'POST',
```

**Generated JS after round-trip:** that `'|url'` line is gone.

**Expected VBP (pipe is not written; value is raw JS, unquoted):**

```
url = baseURL + '/Roo/Category.php';
```

That is a RAW assign. Codegen should emit a raw expression (and must not require a `|` in the VBP name). Open point: whether generated JS key stays legacy `'|url'` or becomes `url` — product decision; VBP must not contain the pipe character in the name.

### Example B — `|sortInfo` (object literal stored as a string today)

**File:** `/home/alan/gitlive/Pman.Admin/old/Pman.Tab.AdminPermProjects.bjs`

**In BJS:**

```json
"|sortInfo": "{ field : 'name', direction: 'ASC' }"
```

**In-memory tree:**

```json
{
  "node-type": 2,
  "prop-name": "|sortInfo",
  "prop-val": "{ field : 'name', direction: 'ASC' }"
}
```

**Writer outputs today (wrong):**

```
|sortInfo = "{ field : 'name', direction: 'ASC' }";
```

Same parse failure; prop lost.

**Generated JS before:**

```js
'|sortInfo' : '{ field : \'name\', direction: \'ASC\' }',
```

**Generated JS after:** line gone.

**Expected VBP** — value is an object literal, use the `@` fence (same rule as other RAW objects), name without pipe:

```
sortInfo = @{ field : 'name', direction: 'ASC' };
```

Not a quoted string. Dequoting alone is not enough for object/array shapes; that is what `@{}` / `@[]` are for.

### Example C — `title` with `{TEMPLATE_VARIABLE}` (different case — not a pipe name)

**File:** `/home/alan/gitlive/Pman.Admin/Pman.Dialog.AdminTranslateTemplates.bjs`

**In-memory tree:**

```json
{
  "node-type": 3,
  "prop-name": "title",
  "prop-val": "\"Note: If the original text contains template variables like  {TEMPLATE_VARIABLE} <br/>Be careful to retain them otherwise the translation may not work\""
}
```

(`node-type` 3 = RAW; name has **no** pipe. Value is a JS string literal including the quote characters.)

**Writer outputs today:**

```
title = "Note: If the original text contains template variables like  {TEMPLATE_VARIABLE} <br/>Be careful to retain them otherwise the translation may not work";
```

This is a **string**, not an object. Do not use `@{`. Keep it as a quoted string (or RAW string). Braces inside the string are text. Any `_strings` drift here is Phase 5, not 4.10.

### Rule to implement for 4.10

On write, for a prop whose name starts with `|`:

1. Emit the name **without** the leading `|`.
2. Treat the value as raw JavaScript:
   - if the stripped value starts with `{` or `[` and is not an empty literal → emit `@` + value (object/array fence);
   - otherwise emit the value unquoted as a RAW expression (as in `url = baseURL + '…';`).
3. On read, rebuild whatever in-memory form codegen needs (RAW and/or restoring `|` on the name if NodeToJs still keys on `'|url'`). Prefer fixing codegen to accept `url` as RAW over keeping `|` in VBP.

Corpus size (PROP names with leading `|` in the JS round-trip set): about `|url`×21, `|renderer`×17, `|icon`×13, `|sortInfo`×5, `|fields`×5, plus a few others.

## Phase 3 — JavaScript round-trip: use the braced-code standard

Status: done — tokenizer line-scans code bodies; **0 FAIL** (2026-08-28)

### 3.1 Emit / store (done)

Writer + `CodeParts` — canonical shape:

```
Function renderer = function(v,x,r) {
  return v;
}
```

Not flat:

```
renderer = function(v,x,r) { return v; };
```

### 3.2 Read back (done)

Parser `take_assign_code()` / `take_code_parts()` split `header {` + body from the `{}` group.

### 3.3 Tokenizer (done)

**Rule:** code body `{` → line-scan to `}` at opener indent. Interior is opaque text.

Opener detection uses `line_prefix` (text on the line before `{`):

```
click function (e) {          ← ends with )
Function renderer = function(v,x,r) {   ← = function…
renderer = function(v) {     ← = function…
Boolean hidden = (function() { ← IIFE; closer `})()` at same indent
  return 1;
})()
data                         ← bare method name; `{` on next line
{
  (function() { … })()
}
```

Wrong Writer emit (content below statement indent — never do this):

```
Boolean hidden = (function() {
    return 1;
})();
```

Right (closer at pad):

```
Boolean hidden = (function() {
  return 1;
})()
```

Wrong (structural scan inside the body — quotes / `[` / nested `{` break):

```
Unterminated string
Unmatched ]
```

Wrong (opaque-at-BOL on every `{` — treats `@[` RAW literals as code bodies):

```
fields = @[
    {
        'name': 'id',
    }
];
```

That `{` is a JSON-ish object inside `@[]`, not a listener body. Only opaque when the line before `{` is a code header (`) {`, `= function…`, `init`, bare method name, etc.).

Structural (unchanged): `Roo.LayoutRegion {`, `layout = Roo.BorderLayout {`, `@[ { … } ]`.

Check:

```bash

grep '^FAIL ' /tmp/rt-js.log | wc -l    # → 0
```

## Phase 4 — Generated JavaScript must match after VBP round-trip

Status: **one open item — 4.10** (documented at the **top** of this file).  
4.1–4.8 fixed. 4.3 / 4.9 → Phase 5. When 4.10 is done, Phase 4 is finished — no further 4.x series from leftover `GEN_DIFF` counts.


### What this phase is

Phase 3 is done: every file **parses** (no `FAIL`). That only means BJS → VBP → BJS tree load works.

Phase 4 asks a harder question: does the **generated `.js`** from the tree after that round-trip match the `.js` from the tree before?

```
load BJS
  → generate JS          (= “before”)
  → write VBP
  → parse VBP back into tree
  → generate JS again    (= “after”)
```

If before ≠ after (ignoring whitespace / comment noise), the test prints:

```
GEN_DIFF Pman.Dialog.Login.bjs
```

So: **same UI tree went through VBP and came back producing different JavaScript.** Something in Writer, Parser, or codegen is changing meaning (or dropping / inventing props).

`FAIL` = could not parse. `GEN_DIFF` = parsed fine, but the JS output changed.

**Out of scope here:** `_strings` / `_named_strings` catalog matching — that is the Phase 5 sidecar. Phase 4 is structural / meaning diffs in the generated widget JS.

### How to look at one file

```bash
./tests/test_vbp_roundtrip.sh tests/vbp-roundtrip-js.manifest build/vbp-roundtrip-js 2>&1 | tee /tmp/rt-js.log
grep '^GEN_DIFF ' /tmp/rt-js.log
```

For each name, diff the two generated files (paths are flat under the project dir):

```bash
diff -u \
  build/vbp-roundtrip-js/Pman.Admin/Pman.Dialog.Login.bjs.original.generated.js \
  build/vbp-roundtrip-js/Pman.Admin/Pman.Dialog.Login.bjs.roundtrip.generated.js
```

Also useful: the VBP itself and the two BJS snapshots:

```
…Login.bjs.vbp
…Login.bjs.original.bjs
…Login.bjs.roundtrip.bjs
```

Fix Writer / Parser / `NodeToJs` until that file drops off `GEN_DIFF`. Repeat.

### 4.1 Fixed — `@[` / `@{` for array/object props

Wrong (unfenced → treated as children / broken JS):

```
sortInfo = { field : 'event_when', direction: 'DESC' };
```

Right:

```
sortInfo = @{ field : 'event_when', direction: 'DESC' };
fields = @[ { name: 'id', type: 'int' } ];
```

### 4.2 Fixed — quote string props that look like enums

Wrong VBP (unquoted → not a string → no translation entry, broken JS):

```
loadingText = Searching...;
```

Right VBP:

```
loadingText = "Searching...";
```

(How that string later appears in `_strings` / the catalog sidecar is **Phase 5** — not the Phase 4 check.)

### 4.3 Not Phase 4 — `_strings` / named_strings noise

We already decided: translation catalog lives in a **separate `.bjs` sidecar** (Phase 5). Do not treat `_strings` / `_named_strings` drift in generated JS as the Phase 4 work item.

**Login example — show the trigger, not the symptom.**

Trigger in VBP:

```
String name = "logout_other_windows";
Mixed value = 0;
```

(also nearby: `String valueOff = 0;`)

What happens today:

- Original tree: `value` is a normal PROP → `findTransStrings` sees prop name `value` (in `doubleStringProps`) and stores `"0"` in `_strings` / `logout_other_windows_value`.
- After VBP: same line often comes back as RAW → `findTransStrings` skips RAW → those lines vanish → `GEN_DIFF` on the string table.

That is not a real UI/codegen bug worth chasing in Phase 4:

```
value = 0;    ← number — should never be a translation string
```

Ignore numeric / non-text values in the translation walk (or strip `_strings` / `_named_strings` from the GEN_DIFF compare). Real named-string catalog work stays in Phase 5.

### 4.4 Fixed — `@` fence leaks into generated JS

**Was ~89 files.** Trigger in VBP (correct):

```
sortInfo = @{ direction : 'ASC', field: 'id' };
```

Wrong JS after round-trip (`take_assign_code` treated `@` as a code header):

```js
sortInfo : @ {
```

Right JS:

```js
sortInfo : { direction : 'ASC', field: 'id' },
```

Fix: `take_assign_code` returns null when RHS starts with `@`; `take_value` stores `{ … }` / `[ … ]` only.

### 4.5 Fixed — typed `Function … = function() { };` missing semicolon (~60 files)

Trigger was Writer `put_code` with no `;` after object-body assigns:

```
Function valueRenderer = function() {
  return String.format("<span style='color:red;'>{0}</span>", ret);
}                    ← missing ;
Number width = 900;
```

`take_value` reads to `;` and ate `Number` into the function body.

Fix: `put_code(..., semicolon)` — `true` for `name = function… { };`, `false` for list peers / `init`.

### 4.6 Fixed — IIFE `(function… { … })()` trailer

Only format we use. Helpers on `CodeParts`:

```
is_iife_header("(function() …")  → true
iife_trailer()                   → ")()"
```

Trigger (method or prop):

```
data (function() {
  return ret;
})()
```

Was: `take_code_parts` dropped tokens after `}`, so `)()` vanished.  
Now: capture trailer after `{}`; if IIFE header and trailer empty, default `)()`.

### 4.7 Fixed — do not `@`-fence empty `[]` / `{}`

Rule from 1.0 was too blunt: “RAW starts with `[`/`{` → emit `@`”.  
Real reason for `@`: nested content would be misread as VBP children.

Needs `@`:

```
fields = @[
  { 'name': 'id', 'type': 'int' }
];
```

Does **not** need `@` — nothing inside:

```
fields = [];
```

Was (Writer always prefixed `@`):

```
fields = @[];
```

Tokenizer then glued `@[]` into one TEXT token → prop_val `"@[]"` → JS `fields : @[]`.

Now Writer skips the fence when the literal is empty (`[]` / `[ ]` / `{}` / `{ }`):

```
fields = [];
```

### 4.8 Fixed — METHOD value starting with `[` → RAW

Legacy `| data` arrays are not functions. In `CodeParts.normalize_tree` (before VBP write):

```
if METHOD and prop_val starts with `[` → node_type = RAW
```

**File:** `/home/alan/gitlive/Pman.Admin/Pman.Dialog.AdminWatch.bjs`

Was:

```
methods [
  data
  {
    [ ['days'], … ]
  }
]
```

Now:

```
data = @[
  ['days'],
  ['hours'],
  ['minutes']
];
```

### 4.9 Noise — `_strings` only

Login `value = 0`, template titles entering `_strings`, etc. — **Phase 5**. Not a Writer/Parser format bug.

Full BJS → wrong VBP → missing JS for `|url`, `|sortInfo`, and the separate `title` string case are under **Remaining Phase 4 work** at the top. That is the only open Phase 4 series.
