## Purpose

- **🔷** Introduce a human-readable **`.vbp`** format (grammar-based, not indentation-significant) as an alternative to JSON **`.bjs`**.
- **🔷** Keep BJS strengths: inlined code (listeners, methods, init) as **opaque text**, object tree, named property objects.
- **🔷** Improve on BJS: readable grammar **and** first-class **documentation** in the file (today’s `doc` field is underused because JSON is hostile to it).
- **🔷** Drop BJS pain: numeric `node-type`, short `$` / `|` / `#` / `*` markers, stuffing named props into `children` via `prop-name`.
- **🔷** Object **names** appear in the grammar as `Type Name { … }` (replaces file-level `id = "…"`).
- **🔷** Need a **parser** (VBP → in-memory `Node` / `NodeProp` tree) and a **writer** (tree → VBP).
- **⏳** Lock grammar edge cases listed under **Grammar risks**.
- **⏳** Decide dual-format policy (`.bjs` forever vs migrate) under **Migration**.
- **ℹ️** Mock conventions already sketched in the sample headers (`;` statements, `,` list peers, `{ }` / `[ ]`, `=`).

## Current behaviour

- **ℹ️** Files are `.bjs` JSON; `bjs-version` 3 uses `tree` + `node-type` ints.
- **ℹ️** Legacy v1/v2 uses `items` + FileLegacy conversion.
- **ℹ️** `oid` is assigned per file for node maps; `id` prop is the human / codegen name.
- **ℹ️** Named child objects use `* prop` / `prop-name` on a child in `children` (kludge).

## Proposed behaviour (format contract so far)

- **🔷** Grammar owns structure; indentation is cosmetic.
- **🔷** Tokens:
  - `{ }` — object bodies, `construct` blocks, handler / method bodies
  - `[ ]` — lists: anonymous children, `listeners`, `methods`
  - `;` — end statement
  - `,` — separate peers inside `[ ]`
  - `=` — assignment
- **🔷** Widgets: `Type` or `Type Name { … }` ; empty `Type {}` allowed.
- **🔷** Anonymous children only in bare `[ … ]`.
- **🔷** `listeners [ … ]` / `methods [ … ]` — list keywords; **`,` between peers**.
- **🔷** Named object props are assignments: `start_child = Gtk.Box viewbox { … }`.
- **🔷** Array slots: `colModel[] = Roo.grid.ColumnModel { … }` (repeatable name).
- **🔷** Non-plain kinds — see **Kinds and specials** (do not treat `special` as one opaque bucket).
- **🔷** Plain GObject/Roo props omit type when inferable from parent FQN.
- **🔷** JS prop values are **expressions**, not only `function (…) { … }`:
  - `renderer = function (v) { … };`
  - `(function () { … }).defer(100);` as a full RHS (old `$` / RAW)
  - `url = baseURL + '/Roo/core_company';`
  - No mandatory `code` wrapper when the RHS is a normal JS expression
- **🔷** File header metadata: `name = …`, `vbp-version = 1`, optional `parent` / `permname` / `using`.
- **🔷** Do **not** emit file `path` in VBP — old JS dump hangover; not author-facing.

## Kinds and specials

### What `NodePropType.SPECIAL` is today

- **ℹ️** Old marker `*`; stored in `node.specials` (not ordinary GIR props).
- **ℹ️** Codegen ignores them as widget properties (`NodeWriter.globalIgnore` for `pack` / `init`, etc.).
- **ℹ️** Doc comment in `Node.vala` lists the classic set: `* prop`, `* args`, `* ctor`, `* init`.
- **ℹ️** Real Builder4 + Roo usage is a **small fixed vocabulary**, not an open-ended “anything special”:

Inventory (v3 `node-type` SPECIAL + legacy `* …` keys):

- **`pack`** — how this node is attached to its parent
  - `false` / empty → do not pack (e.g. notebook tab labels)
  - method name → `set_start_child`, `append`, …
  - method + extra args → `append_page,_this.label_preview.el`
  - ℹ️ Vala: `NodeToVala.packChild` splits on comma
- **`init`** — code run after the instance exists (construction hook body)
  - BJS name; Vala’s closest term is **`construct { }`**
- **`ctor`** — alternate constructor **expression** (which `new …` to call)
  - e.g. `new Gtk.Scale.with_range(…)` / `new Gtk.Popover()`
- **`args`** — ctor argument list string (legacy `* args`; mostly top-level / rare)
- **`columns`** — packing helper for multi-column add (rare)
- **`response_id`** — dialog action-widget response (rare)
- **`title`** — occasional builder title special (rare; confirm vs real prop)
- **`xinclude`** — Roo include path (Roo-only)
- **`* prop`** — **not a codegen hook**; names the **parent property slot** this object fills (`center`, `layout`, `child`, `colModel[]`, …)

### What must leave the `special` bucket in VBP

- **🔷** `* prop` / named child objects are **property assignments**, not `special`:
  - `start_child = Gtk.Box viewbox { … }`
  - `layout = Roo.BorderLayout { … }`
  - That was the BJS children+`prop-name` kludge; VBP already rejects stuffing them into `[ ]`.
- **🔷** Today’s `* init` is a **code block**, not a property value:
  - **🚫** `init = …;` / `construct = …;` — assignment + semicolon is the wrong shape
  - **🔷** Dedicated block keyword, aligned with **Vala**: **`construct { … }`**
  - Maps to SPECIAL/`init` for existing codegen; mimics Vala’s `construct { }`
  - **🚫** Long-term spelling `code init { … }` (mock only)
- **🔷** `pack` — see dedicated **Pack** section (several viable options; not just one spelling).

### Proposed VBP surface (to lock)

Split the old `SPECIAL` enum into **named roles** in the text format. Parser still may map them back to `NodePropType.SPECIAL` + `prop_name` for codegen compatibility.

- **🔷** `⏳` **`pack`** — see **Pack** (options A–D); do not freeze one spelling until that section is locked.
- **💩** `⏳` When parent uses `start_child =` / `end_child =`, writer omits redundant child-side pack (depends on Pack option).
- **🔷** `⏳` **`construct { … }`** — first-class **block** (not an assignment):
  - Keyword + `{` … `}` only — no `=`
  - ↔ stored as SPECIAL name `init` for `NodeToVala` init emission
- **🔷** `⏳` **`ctor`** — constructor **expression** (value-like; `;` OK), distinct from `construct`:
  - `ctor = new Gtk.Popover();`
  - Picks/builds the `new …` call; `construct { }` is the construct body
- **🔷** `⏳` **`args`** — first-class if still needed (value-like):
  - `args = foo, bar;`
- **🔷** `⏳` **`var`** — instance fields (typed); maps to `NodePropType.USER`. **Default access is public.**
  - `var Type name = value;` — public (preferred spelling)
  - `public Type name = value;` — same as `var`
  - `private Type name = value;` / `protected Type name = value;`
  - **🚫** `public var` / `private var` — access keyword replaces `var`, it is not a modifier in front of `var`
- **🔷** `⏳` **`listeners [ … ]` / `methods [ … ]`** — list keywords; bodies are blocks inside peers; **`,` separates peers** (same as anonymous children in bare `[ ]`).
- **💩** `⏳` Drop the leading word **`special`** entirely once the vocabulary above is locked.
- **💩** `⏳` Keep `special Name = …` only as an **escape hatch** for rare keys (`columns`, `response_id`, `xinclude`) until each earns a keyword.
- **💩** `⏳` Roo: same shell keyword `construct` vs JS-dialect `init` — prefer one shell keyword if storage stays `init`.

### Why one `special` keyword is the wrong default

- **🔷** It hides **different semantics** (attach vs ctor expression vs construct body vs named slot) behind one word.
- **🔷** Named slots are already expressed by **`Name = Type { }`** — calling that `special` fights the VBP model.
- **🔷** Parser/writer and UI need the same vocabulary as codegen (`packChild`, init/`construct` emission, ctor line).
- **ℹ️** `NodePropType.SPECIAL` can remain the **storage** enum during transition; the **file text** should name the role.

### Syntax families (kinds)

- **🔷** **Value statements** (end with `;`): plain props, `var` / `public` / `private` / `protected` fields, `pack`, `ctor`, `args`, RAW expressions.
- **🔷** **Blocks** (keyword + `{ … }`, not `Name =`): `construct` (and bodies inside listener/method peers).
- **🔷** **Object literals** (`Type` + optional Name + `{ … }`): widgets / named prop objects.
- **🔷** **Lists** (`listeners [ … ]` / `methods [ … ]` / bare `[ … ]`): `,` between peers.

### Open locks (kinds)

- **🔷** `⏳` Spelling locked to preference **`construct`** (Vala) over file-text `init` — confirm once and update mocks.
- **🔷** `⏳` **Pack** — pick among options in **Pack** (child `pack =`, parent named props, hybrid, …).
- **💩** `⏳` Roo `* prop` for `colModel[]` / `dataSource` — already `prop[] =` / `prop =`; confirm no leftover `special`.
- **💩** `⏳` `title` special vs plain `title =` prop — audit DialogFiles / project popovers before granting a keyword.

## Pack

### What pack does today

- **ℹ️** SPECIAL / `* pack` on the **child** tells codegen how to attach that child to its parent.
- **ℹ️** `NodeToVala.packChild`:
  - `pack = false` (or `true` — same branch) → **skip** packing
  - `pack = method` or `method,arg,arg,…` → emit `parent.method(child, args…)`
  - no pack → heuristics by parent FQN (GTK4 `set_start_child`, notebook pages, `add_controller`, etc.)
- **ℹ️** `NodeToGtk` / Glade path also splits `* pack` on commas and maps extra args onto method params / child properties.
- **ℹ️** Common real values from Builder4:
  - `false` — e.g. notebook tab labels that must exist as children but not be packed as pages
  - `set_start_child` / `set_end_child` — Gtk.Paned / similar
  - `append_page,_this.label_preview.el` — notebook page + tab widget ref
  - `get_content_area().append` — dialog content (method path string)

### Tension with VBP named props

- **🔷** VBP already wants **`start_child = Gtk.Box viewbox { … }`** instead of a child in `[ ]` with `pack = set_start_child`.
- **🔷** That removes a large class of pack strings for GTK4 **property** children.
- **🔷** Pack must still cover what named props **cannot**:
  - **opt-out** (`false`) for siblings that live in the tree but are not packed
  - **multi-arg attach** (`append_page`, tab label ref)
  - **odd method paths** (`get_content_area().append`)
  - **Roo** packing / `* prop` patterns that are not GTK child properties

### Options (pick intentionally)

**Option A — Keep child-side `pack = …;` (closest to BJS)**

- **🔷** Child in `[ ]` (or under parent) carries:
  - `pack = false;`
  - `pack = set_start_child;`
  - `pack = append_page, _this.label_preview.el;`
- **ℹ️** Pros: maps 1:1 to current SPECIAL + `packChild`; writer/reader simple.
- **ℹ️** Cons: duplicates GTK4 child properties; comma-in-value is a lexer hazard; stringly method names.

**Option B — Prefer parent named props; pack only for exceptions**

- **🔷** Default attach = parent assignment: `start_child = Gtk.Box viewbox { … }`.
- **🔷** Anonymous `[` children use palette default packing (today’s no-pack heuristic).
- **🔷** Explicit `pack = …` only when needed: `false`, multi-arg, weird methods.
- **ℹ️** Pros: matches VBP “named props are assignments”; less pack noise in mocks (Paned already).
- **ℹ️** Cons: two ways to say the same thing during migration; writer must choose named prop vs pack.

**Option C — Pack as a small structured form (not one comma-string)**

- **💩** e.g. `pack append_page(_this.label_preview.el);` or:
  - `pack { method = append_page; args = _this.label_preview.el; }`
- **ℹ️** Pros: avoids comma-as-separator ambiguity; clearer for parser.
- **ℹ️** Cons: new syntax; further from BJS; more writer work.

**Option D — Opt-out only as a flag; everything else is parent-side**

- **💩** `packed = false;` (or `pack = false;`) as the **only** child-side pack keyword.
- **💩** All positive attach expressed as parent props / methods in the parent object (including inventing `pages[] =` / notebook helpers later).
- **ℹ️** Pros: smallest child-side vocabulary; cleanest long-term GTK4 story.
- **ℹ️** Cons: notebook `append_page` + tab label and dialog `get_content_area().append` need a **parent-side** story before this is complete; not free for v1.

### Lean (for review)

- **🔷** Prefer **Option B** for v1: named parent props first; retain child `pack = …;` for opt-out and multi-arg / odd methods.
- **🔷** `⏳` Writer rules:
  - If child was only expressing a known GTK child property via pack → emit parent `prop = Type Name { }` and **no** pack
  - If `pack = false` → keep on child
  - If pack has extra args or unknown method → keep `pack = method, args…;` on child
- **💩** `⏳` Later migrate toward **Option D** once notebook/dialog attach has a parent-side representation.
- **🚫** Do not require Option C for v1 unless comma parsing proves too painful.

### Pack-specific grammar notes

- **🔷** `⏳` `pack = …;` is a **value statement**; RHS is an expression/list until `;` at depth 0 (string-aware).
- **🔷** `⏳` Commas inside pack RHS separate method vs args — same hazard called out under **Grammar risks**; collapse pack RHS as EXPR.
- **🔷** `⏳` `pack = false` / missing pack / default heuristic must stay distinguishable for round-trip of “intentionally unpacked” nodes (tab labels).

## Object IDs and names

### Two layers

- **🔷** **Author name (user-facing):** `id` prop / VBP `Type Name` / Vala `xvala_id`.
- **🔷** **Runtime key (`oid`):** per-file `int` on `NodeBase`, indexed in `JsRender.nodes`.
- **ℹ️** Comment in `JsRender.vala`: OID map is **managed by Action classes, should not be used elsewhere**.

### Why `oid` exists (from the code — not a product feature)

- **ℹ️** Undo/redo (`Action.Add` / `Move` / `Remove` / `ChangeProp`) stores `nodeOid` / `parentOid` and resolves with `file.nodes.get(oid)` after the tree mutates.
- **ℹ️** Drag-drop in `WindowLeftTree` uses `oid` in the drag payload and `drop_nid` so drop targets survive async hops without holding live pointers.
- **ℹ️** Node equality / “same node?” checks compare `oid`.
- **ℹ️** Fallbacks when the author never set `id`:
  - codegen name `%s%d`.printf(xtype, oid) in `NodeWriter`
  - Glade id `w` + oid in `NodeToGlade` / `GtkView`
  - `uid-%d` style keys in `Node`
- **ℹ️** BJS v3 JSON **serializes** `oid` when ≠ `-1`; on load, `setFile` **keeps** an existing oid or calls `nextOid()`.
- **💩** Likely reason it was **persisted** at all: convenience — stable numbers across save/reload for Glade `wN`, debug dumps, and less renumber churn — **not** because authors edit or care about oid.
- **🔷** It is **not** user-facing identity. Authors care about `notebook` / `view`, not `oid: 28`.

### VBP policy

- **🔷** **Do not write `oid` into VBP.**
- **🔷** On load, assign fresh oids via existing `setFile` / `nextOid()` (same as `oid == -1` path today).
- **🔷** Undo / DND / `nodes` map keep using runtime oids after load; they do not need file-stable values once the session starts.
- **🔷** **Author identity in VBP is `Type Name` only** — e.g. `Gtk.Notebook notebook { … }`.
  - That **Name replaces the separate `id = "…"` property** in the file text.
  - No second spelling → no disagree-with-`id` problem.
- **🔷** `⏳` Parser: `Type Name` → set in-memory `id` prop (and thus `xvala_id` / codegen) so the rest of RooBuilder stays unchanged.
- **🔷** `⏳` Writer: if node has `id`, emit `Type Name` and **do not** also emit `id = "…"`.
- **🔷** `⏳` Anonymous objects: `Type { … }` with no Name when there is no `id` (codegen keeps oid-based fallbacks as today).
- **💩** `⏳` Optional later: allow renaming in the UI to edit Name in place (same as today’s edit-`id`).
- **ℹ️** Vala codegen still reads the `id` **prop** internally (`NodeWriter.globalIgnore("id")` for GObject packing) — VBP just stops **writing** `id` as a visible assignment.
- **🚫** Do not keep both `Gtk.Box view` and `id = "view"` in canonical VBP output.

## Grammar risks

- **🔷** `⏳` Structural parse must sit on a **string-aware tokenizer** — see **Lexer then structural parse**.
- **🔷** `⏳` Vala listeners `clicked ( ) => { … }` vs Roo `click () { … }` vs JS RHS expressions — one outer grammar, dialect differences in value shape.
- **🔷** `⏳` JS assignment RHS is a **full expression** terminated by `;` at brace/paren depth 0 (only counting braces **outside** strings):
  - `renderer = function (v) { return v; };`
  - `foo = (function () { … }).defer(100);`
  - `url = baseURL + '/Roo/core_company';`
- **💩** `⏳` Whether multi-statement RHS without wrapping `(function(){ … })` is allowed — probably not; one expression per `Name = … ;`.
- **🔷** `⏳` Nested `[` lists: children vs `listeners` vs `methods` vs JS `fields = [ … ]` — disambiguate by keyword / LHS; `[` inside strings is not structure.
- **🔷** `⏳` Property values that look like types: `orientation = Gtk.Orientation.VERTICAL` vs child `Gtk.Label { }`.
- **🔷** `⏳` `pack = append_page, _this.label_preview.el` — commas inside a pack value must not start a new list peer (comma tokens only at depth 0 outside strings).
- **💩** `⏳` Trailing commas in `[ ]` — allow (JS-like) or forbid.
- **💩** `⏳` Optional `;` after `}` for assigned objects (`center = Roo.LayoutRegion {};`) — mock allows it; lock as required vs optional.
- **🚫** `#` line comments in the VBP shell — avoid; use `/** */` for docs only. Vala/JS bodies may still contain `//` / `/* */` as opaque code.
- **💩** `⏳` `using Gtk 4.0` header — parse and store, or ignore until needed for Blueprint interop.

## Lexer then structural parse

### Why strings first

- **🔷** Braces / brackets / `;` / `,` **inside strings** must not affect structure.
- **🔷** Harder than brace-depth alone: wrong string rules → false structure or swallowed code.
- **🔷** VBP embeds **Vala and/or JS** bodies, so the lexer must recognize **both** families’ string literals (dialect may narrow which apply inside a given body).

### String forms to handle

**JS / Roo (code + RAW RHS):**

- **🔷** `'…'` and `"…"` with `\` escapes
- **💩** `` `…` `` template literals (nested `${…}` — only if we allow them in VBP bodies; common in modern JS, rarer in older Roo)
- **ℹ️** Regex literals `/…/` can look like comments or paths — **💩** decide if Roo bodies need regex tokenization or we rely on strings only for v1

**Vala (listeners / methods / `init`):**

- **🔷** `"…"` with escapes
- **🔷** `@"…"` interpolated strings (still end on unescaped `"`)
- **🔷** `"""…"""` / `'''…'''` verbatim (end on matching triple; no escape-for-delimiter in the usual Vala sense)
- **💩** Char literals `'x'` — short; still must not break `'` state if we share a JS-style single-quote rule inside Vala bodies

**VBP file shell (outside code bodies):**

- **🔷** Prefer `"…"` for property strings in the shell
- **💩** Allow `'…'` in the shell for symmetry with Roo samples, or require double quotes only

### Proposed pipeline

- **🔷** `⏳` See sub-plan **[`1.2-vbp-parser.md`](1.2-vbp-parser.md)** for the implementable three-stage pipeline:
  1. **Tokenizer** — flat, string-aware tokens
  2. **Token tree** — nest `{ }` / `[ ]`
  3. **Structural pass** — tree → `Node` / `NodeProp` (bodies opaque)
- **🔷** `⏳` **Phase A — tokenize** the whole file into a flat token stream:
  - structural: `{` `}` `[` `]` `(` `)` `;` `,` `=` `=>`
  - words / keywords: `var`, `public`, `private`, `protected`, `pack`, `construct`, `ctor`, `listeners`, `methods`, type names, identifiers
  - **string** tokens (payload preserved verbatim, including delimiters)
  - **comment** tokens (or discarded — except doc comments; see **Documentation**)
- **🔷** `⏳` **Phase B — token tree** then **structural parse:**
  - Nest brace/bracket groups once (easier than re-deriving depth in a single recursive-descent over raw text)
  - Collapse token runs that belong to a code/expression body into **one opaque** blob / source slice
  - Parse only VBP shell elements: headers, `Type Name { }`, assignments, `[` lists (`listeners` / `methods` / children), pack/init/ctor
  - Opaque blob → `prop_val` text (same as today’s almost-uninterpreted RHS)
- **🔷** Vala listeners and Roo listeners are **reasonably similar** in shape (`name (args) … { body }`); one list grammar covers both; body text stays dialect-specific.
- **🔷** Matches current BJS behaviour: RHS / listener / method bodies are **stored as text** and handed to codegen — not interpreted as an AST.
- **🔷** Structural components (`{ }` objects, `[ ]` lists, `Name =` statements) are **reasonably collapsible**; that is why a small token set + collapse is enough.
- **🚫** Line-based or indent-based structure.
- **🚫** Full Vala/JS language server / AST in the VBP parser v1.
- **🚫** Regex-only “match braces” without a string state machine.

### Open locks (lexer)

- **🔷** `⏳` One lexer with a **dialect mode** (shell / vala-body / js-body) vs union of string forms everywhere (union is fine if collapse treats bodies as opaque after depth rules).
- **💩** `⏳` Template literals and regex literals in v1, or defer.
- **💩** `⏳` Whether `pack = …` values are tokenized as EXPR (comma-aware at depth 0) or raw-to-semicolon.

## Documentation

- **🔷** Current BJS has a `doc` field on `NodeBase` / props, but **authoring docs in the file is severely lacking** in practice (JSON is hostile to readable comments).
- **🔷** VBP should make documentation a **first-class, human** part of the format.
- **🔷** `⏳` Docs attach as **`/** … */`** immediately above a node / prop / listener → `doc` on parse.
- **🔷** `⏳` Writer: emit `/** … */` when `doc` is non-empty (round-trip).
- **🚫** **`#` line comments** in VBP — avoid at all costs (not for docs, not for file headers in examples).
- **💩** `⏳` File-level module doc as a leading `/** */` under/before the header.
- **🚫** Do not silently drop `doc` on VBP write.

## Parser issues

- **🔷** `⏳` Entry: detect `.vbp` (and/or content sniff) beside existing JSON `.bjs` path in load.
- **🔷** `⏳` Output of parse must be the **same** in-memory model as BJS v3 (`Node` / `NodeProp`, `NodePropType`, `children`).
- **🔷** `⏳` Map kinds → `NodePropType` (see **Kinds and specials**):
  - plain assign → `PROP`, or `RAW` when the RHS is an unquoted JS/Vala **expression** (urls, `(function(){}).defer(100)`, etc.)
  - `var` / `public` / `private` / `protected` → `USER` (`var` and `public` = public access; writer emits `var` for public)
  - `pack` / `ctor` / `args` / rare escape keys → `SPECIAL` + that `prop_name` (storage compatibility)
  - `construct` / `init` storage → `SPECIAL` name `init` (file keyword **`construct`**)
  - `listeners` entries → `LISTENER`
  - `methods` entries → `METHOD`
  - object → `OBJECT`
  - **🚫** Do not map named object props through `SPECIAL` / `* prop` — they are object nodes with `prop_name` set via assignment
- **🔷** `⏳` Named prop objects: set `prop_name` on the object node **without** requiring it to live only as a fake child packing kludge — align with current children+prop_name model or a cleaner store (confirm against `docs/node_to_nodeprop.md`).
- **🔷** `⏳` USER access: `NodeBase.prop_access` — empty/`""` = public (`var` or `public` in the file). Writer and `NodeToVala.addMyVars` emit `private` / `protected` when set.
- **🔷** `⏳` Error reporting: file + line + column (JSON parser errors are weak today; VBP should be better).
- **💩** `⏳` Incremental parse / editor language server — out of first parser milestone.
- **💩** `⏳` Recover after syntax error (skip to next statement) — optional.
